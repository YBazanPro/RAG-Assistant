# ADR 0002: Identity and Authentication

> **Naming note (2026-10-15):** the backend project `RagAssistant.Host` has since been renamed `RagAssistant.Api` (Aspire resource `api`, configuration keys `services:api:*`, test stub `StubApi`). "The Host" in this document means that project.

**Status:** Accepted
**Date:** 2026-10-13
**Amends:** [ADR 0001](0001-ui-ai-streaming-stack.md), decision 5 (UI hosting)

## Context

`product.md` defines three personas: Knowledge Seeker, Content Owner and System Maintainer. They have different rights: asking questions, managing the corpus, and diagnosing the system. The application needs authentication and role-based authorization that:

- runs locally as a Docker container orchestrated by Aspire;
- is free;
- defines its users and roles **in files committed to the repository**, so that anyone who clones the repo can start the solution and sign in with no manual setup;
- lets every persona be tested automatically.

Candidates considered: Keycloak, Zitadel, Dex, Authelia, mock-oauth2-server, a custom OpenIddict server, and Duende IdentityServer.

## Decisions

### 1. Identity provider: Keycloak, dev-only, configured by realm import

Keycloak (Apache 2.0) runs as a container in the AppHost through `Aspire.Hosting.Keycloak`. The Host and Web projects use `Aspire.Keycloak.Authentication`. Both packages are **preview**; their versions are pinned in `Directory.Packages.props`.

```csharp
var keycloak = builder.AddKeycloak("keycloak", port: 8180)
    .WithRealmImport("./Realms");
```

- **Realm file:** `src/RagAssistant.AppHost/Realms/ragassistant-realm.json` is the single source of truth for clients, roles, users and token settings.
- **No data volume:** the container starts fresh on every run and re-imports the realm. Keycloak imports a realm only when it does not already exist, so a volume would silently ignore edits to the file.
  - Any change made in the admin console is lost on restart. Changes go in the file.
- **Fixed port** (8180), so that the issuer URL is stable across runs.
- **Admin console password:** generated by Aspire into the AppHost user secrets, like the Postgres password.
- **Image tag:** pinned, and identical in the AppHost and the Keycloak test container, following the same rule as the Postgres image.

**Rejected:**

| Candidate | Reason |
|---|---|
| Zitadel | Users and roles are created through its API or Terraform after startup, so a fresh clone would need a provisioning step. |
| Dex | Its built-in (static) users cannot have groups or roles, so personas cannot be tested. |
| Authelia | Built mainly for reverse-proxy login; its OIDC setup is fiddly locally (cookie domains, HTTPS). |
| mock-oauth2-server | A mock, suitable for tests but not credible as the demo's identity provider. |
| Custom OpenIddict server | Writing and maintaining an identity provider is out of proportion for this project. |
| Duende IdentityServer | Commercial license. |

### 2. Realm content

**Realm:** `ragassistant`.

**Clients:**

| Client | Type | Purpose |
|---|---|---|
| `ragassistant-web` | Confidential, authorization code + PKCE | Sign-in for the Web BFF |
| `ragassistant-api` | Audience only (no login) | Access tokens must carry `aud: ragassistant-api` (audience mapper on the web client) |

**Roles** are realm roles mapped to the personas. They are composite, so each higher role includes the rights of the roles below it:

| Role | Persona | Includes |
|---|---|---|
| `knowledge-seeker` | Knowledge Seeker | — |
| `content-owner` | Content Owner | `knowledge-seeker` |
| `maintainer` | System Maintainer | `content-owner` |

**Users:** one test user per role. Usernames and dev passwords are listed in the README.

**Token shape:**
- A protocol mapper emits realm roles as a **flat `roles` claim**. Keycloak's default nested `realm_access.roles` claim is not understood by ASP.NET Core.
- The access-token lifetime is long enough for comfortable local use; refresh is still implemented (decision 4).

**Committed secrets:** the realm file contains dev user passwords and the web client secret. This is acceptable **only** because the file is used exclusively for local development. It is never deployed. A real environment uses its own identity provider configuration, which is out of scope here.

### 3. API (Host): JWT bearer authentication and role-based policies

```csharp
builder.Services.AddAuthentication()
    .AddKeycloakJwtBearer("keycloak", realm: "ragassistant", options =>
    {
        options.Audience = "ragassistant-api";
        options.TokenValidationParameters.RoleClaimType = "roles";
    });
```

- `RequireHttpsMetadata` is disabled in Development only.
- Policy names are constants in `RagAssistant.Shared` (names only, no logic). Endpoint groups apply them with `.RequireAuthorization(...)`.

| Policy | Required role | Covers |
|---|---|---|
| `KnowledgeSeeker` | `knowledge-seeker` | Chat, reading active documents and passages, citations |
| `ContentOwner` | `content-owner` | Importing, updating, archiving and reprocessing documents |
| `Maintainer` | `maintainer` | `/admin`: request traces, failures, evaluation results |

- **Every API endpoint requires authentication**, except the health checks (Development only).
- **User identity in modules:** modules identify users by the `sub` claim, never by username.
  - Conversations belong to their author: a user sees only their own conversations.
  - Maintainers can read all request traces (Journey 4).

### 4. UI (Web): backend for frontend (BFF), amending ADR 0001 decision 5

ADR 0001 had the WebAssembly client call the Host directly. With authentication, that would put access tokens in the browser. Instead:

- `RagAssistant.Web` signs the user in with OpenID Connect (`AddKeycloakOpenIdConnect`, code + PKCE) and keeps the session in an **HTTP-only, same-site cookie**. Tokens stay on the server (`SaveTokens`).
- `RagAssistant.Web` forwards `/api/**` (REST and SSE) to the Host through **YARP**. A request transform attaches the user's access token as `Authorization: Bearer`.
  - Response buffering stays disabled so SSE events reach the browser as they are produced.
- The WebAssembly client calls only its own origin (`/api/...`) with the cookie. It never sees a token.
- Authentication state reaches WebAssembly components through `AddAuthenticationStateSerialization` (server) and `AddAuthenticationStateDeserialization` (client).
- **Access-token refresh** (refresh-token grant) is handled in the BFF before tokens are forwarded. The library, if any, is chosen at implementation time and must be free and open source. *Amended by [spec 005](../specs/005-web-shell.md): no refresh is implemented. The session lasts as long as the access token (1 hour); after that the next request re-challenges and the Keycloak SSO session signs the user back in without a password prompt.*
- **Antiforgery:** state-changing `/api/**` calls from the client require antiforgery protection, as the cookie authenticates them. *Amended by [spec 005](../specs/005-web-shell.md): the protection is a required `X-Requested-With: ragassistant` header on POST/PUT/PATCH/DELETE plus a `SameSite=Lax` cookie; antiforgery tokens are used only for the sign-out form.*

The rest of ADR 0001 decision 5 still holds: WebAssembly interactivity for streaming pages, and the Host remains the only backend.

### 5. Testing: TUnit, test-issued tokens, plus one realm smoke test

- **Integration tests do not start Keycloak.** `RagAssistantAppFactory` reconfigures JwtBearer (via `PostConfigure<JwtBearerOptions>`) to validate tokens signed with a **test signing key**. The issuer, audience and `roles` claim shape are the same as Keycloak's.
- A helper, e.g. `factory.CreateClientAs(Persona.ContentOwner)`, mints signed tokens, so persona rules are tested with TUnit `[Arguments]`:
  - unauthenticated → 401;
  - wrong role → 403;
  - right role → success.
- **One smoke test** starts Keycloak through Testcontainers with the **same realm file**. It signs in each test user and checks that the access token carries the expected `aud` and `roles`. This catches mistakes in the realm file that the test-key tokens cannot.
- Tests never depend on the dev passwords staying stable, except in that smoke test, which reads them from the realm file.

## Consequences

**Positive**
- Clone, `dotnet run --project src/RagAssistant.AppHost`, and sign in as any persona. No manual setup.
- The realm file is a reviewable, version-controlled description of who can do what.
- Authorization rules are covered per persona by fast tests that need no identity provider.
- Tokens never reach the browser.

**Negative**
- Keycloak is heavy for a dev dependency (about 0.5–1 GB RAM, 15–30 s startup), and its Aspire integration is preview.
- Changes made in the Keycloak admin console are discarded on restart. This is intentional, but may surprise people.
- The BFF adds YARP, token forwarding and refresh, and antiforgery to `RagAssistant.Web`.
- `product.md` must now treat basic persona-based access as part of the first release.

## Revisit when

- The application is deployed beyond a developer machine: choose that environment's identity provider, keep the same roles and claim shape, and never deploy the dev realm file.
- Finer-grained rights are needed (per-corpus or per-document access): extend the policies, possibly with resource-based authorization.
- The Aspire Keycloak packages reach GA, or are discontinued.
