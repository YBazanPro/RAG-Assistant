# Spec 001: Aspire Orchestration with PostgreSQL + pgvector

**Status:** Approved (2026-10-13)
**Date:** 2026-10-13

## Problem

Running RagAssistant locally requires a PostgreSQL instance with the `vector` extension and a connection string wired into the Host by hand. The developer wants a single entry point — a .NET Aspire AppHost — that starts the API and a pgvector-enabled PostgreSQL together, applies database migrations, and shows logs/traces in the Aspire dashboard. Integration tests must run against the same PostgreSQL/pgvector version as development.

## Scope

### In
- **`RagAssistant.AppHost`** (Aspire 13.6.1) — the local development entry point.
- **`RagAssistant.ServiceDefaults`** — standard Aspire template: OpenTelemetry (logs, metrics, traces → dashboard), health checks (`/health`, `/alive`, mapped in Development only), service discovery, standard HTTP resilience. Referenced by the Host and the MigrationService.
- **PostgreSQL container** from image `pgvector/pgvector:0.8.7-pg18-trixie`:
  - Server resource `postgres`, database resource `ragassistant` (connection string name `ragassistant`).
  - **One database**; modules isolate data with **one schema per module**.
  - **Persistent container** (`ContainerLifetime.Persistent`) — keeps running between AppHost runs.
  - **Persistent named volume** `ragassistant-postgres-data` — data survives container recreation.
  - **Fixed host port 5433**.
  - **Password generated by Aspire** once and stored in the AppHost's user secrets (stable across runs; never committed).
- **pgweb** admin UI attached to the server (also persistent lifetime).
- **`RagAssistant.MigrationService`** — worker started by the AppHost that applies all module EF Core migrations, then exits. Created now; with no module DbContexts registered yet it applies nothing and exits successfully.
- **Reusable migration runner** — one class that applies migrations for every registered module DbContext; called by both the MigrationService and the integration-test fixture. Modules make their DbContext known to it through their module registration (exact mechanism decided in `/plan`).
- **`RagAssistant.Host`**:
  - Calls `AddServiceDefaults()` / `MapDefaultEndpoints()`.
  - Gets the database through the Aspire Npgsql client integration using connection name `ragassistant` (includes the Npgsql health check and tracing).
  - Starts only after `postgres` is ready **and** the MigrationService has completed successfully.
- **Integration tests**:
  - Testcontainers PostgreSQL using the **same image** `pgvector/pgvector:0.8.7-pg18-trixie`, one container shared per test session.
  - Connection string injected into `WebApplicationFactory<Program>` as `ConnectionStrings:ragassistant`.
  - Schema brought up to date with the reusable migration runner before tests run.
  - **All** integration tests, including the existing smoke test, require Docker.
- Update `CLAUDE.md`: Aspire in the tech stack, AppHost as the run command, test image `0.8.7-pg18-trixie` (replaces `pg17`), MigrationService in the architecture tree.

### Out
- Any deployment or publishing target (azd, Azure Container Apps, Kubernetes, Aspire publish manifests) — **dev only**.
- Modules, entities, tables, migrations, and the `vector` extension itself (created later by the Documents module's first EF migration via `HasPostgresExtension("vector")`).
- Aspire-based testing (`Aspire.Hosting.Testing`) — tests use Testcontainers directly.
- Redis / HybridCache L2, messaging, auth.

## Domain Model

N/A — infrastructure only. Database `ragassistant`; schemas are created per module by that module's migrations.

## API Contract

No business endpoints. From ServiceDefaults, in Development only:

| Verb | Route | Response |
|------|-------|----------|
| GET | `/health` | 200 when all health checks (incl. Npgsql) pass, 503 otherwise |
| GET | `/alive` | 200 when the process is live (liveness-tagged checks only) |

## Authorization

- Dev only. The PostgreSQL password is generated by Aspire and kept in AppHost user secrets; it is never written to `appsettings*.json` or committed.
- Postgres (5433) and pgweb are reachable on the developer machine only; no further auth.
- Health endpoints are not mapped outside Development.

## Edge Cases & Failure Modes

- **E1 — PostgreSQL 18 data directory layout.** PG18 images changed `PGDATA` to `/var/lib/postgresql/18/docker` and expect the volume at `/var/lib/postgresql`; mounting at the old `/var/lib/postgresql/data` path makes the container fail to start. The volume **must** be mounted where the PG18 image expects it. If Aspire's `WithDataVolume` targets the old path, mount the named volume explicitly at `/var/lib/postgresql`.
- **E2 — Password vs. persistent volume.** The volume keeps the password set at first initialization. If the user-secrets password is lost or changed, the Host cannot connect. Recovery: restore the secret, or delete the `ragassistant-postgres-data` volume (destroys dev data). Document in README.
- **E3 — Port 5433 in use.** The AppHost fails to start the container; the dashboard shows the error. No automatic fallback.
- **E4 — Docker not running.** The AppHost (and integration tests) fail with a clear Docker error; no fallback.
- **E5 — Migration failure.** The MigrationService exits non-zero; the Host does **not** start; the failure is visible in the dashboard logs.
- **E6 — Image tag change.** The tag is pinned to `0.8.7-pg18-trixie` in both the AppHost and the test fixture. Upgrading to a new PostgreSQL **major** version needs a data migration or a fresh volume.
- **E7 — Persistent container config drift.** If the container configuration changes (image, port, env), Aspire recreates the persistent container; the named volume keeps the data.

## Non-Functional Requirements

- Warm start (persistent container already running): the AppHost brings the Host to healthy without recreating the Postgres container.
- The build stays warning-free under `TreatWarningsAsErrors`.
- No new package versions outside `Directory.Packages.props`.

## Integrations

- Docker (container runtime for Aspire and Testcontainers).
- Image `pgvector/pgvector:0.8.7-pg18-trixie` (PostgreSQL 18, pgvector 0.8.7, Debian trixie).
- pgweb container (Aspire `WithPgWeb`).
- Packages (Aspire 13.6.1): `Aspire.AppHost.Sdk`, `Aspire.Hosting.PostgreSQL`, the Npgsql client integration for the Host/MigrationService, plus the ServiceDefaults template packages.

## Acceptance Criteria

- **AC-1** — Given Docker is running and no container exists yet, when I run the AppHost, then a `postgres` container from `pgvector/pgvector:0.8.7-pg18-trixie` starts on host port 5433 with the named volume `ragassistant-postgres-data`, database `ragassistant` exists, and pgweb, MigrationService and Host appear in the dashboard.
- **AC-2** — Given the AppHost is running, when the MigrationService finishes, then it shows as completed successfully, and only after that the Host starts and reports healthy.
- **AC-3** — Given data was written to the database, when I stop the AppHost and start it again (and also after the container is removed and recreated), then the data is still present and the Host connects with the same password.
- **AC-4** — Given the AppHost is stopped, when I check Docker, then the `postgres` and pgweb containers are still running (persistent lifetime).
- **AC-5** — Given the Host runs under the AppHost in Development, when I call `GET /health`, then it returns 200 and includes the Npgsql check; `GET /alive` returns 200.
- **AC-6** — Given the Host runs under the AppHost, when I open the dashboard, then the Host's logs, traces and metrics are visible.
- **AC-7** — Given I open pgweb from the dashboard, then I can browse the `ragassistant` database.
- **AC-8** — Given I connect an external client to `localhost:5433` with the credentials from the dashboard/user secrets, then the connection succeeds.
- **AC-9** — Given Docker is running, when I run `dotnet test --solution RagAssistant.slnx`, then the test session starts one `pgvector/pgvector:0.8.7-pg18-trixie` container, runs the migration runner against it, the Host smoke test passes, and the container is removed afterwards.
- **AC-10** — Given the repository, when I search for the PostgreSQL password, then it appears in no tracked file.
- **AC-11** — Given the solution, when I run `dotnet build RagAssistant.slnx`, then it succeeds with zero warnings.
- **AC-12** — `CLAUDE.md` documents Aspire, the AppHost run command, the MigrationService, and test image `0.8.7-pg18-trixie`.
